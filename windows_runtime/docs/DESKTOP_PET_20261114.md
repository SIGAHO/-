# Breaktailの画面キャラ（初回試作）

ユーザー提供の64×64・3コマGIFをWindowsの最前面に表示する。移動と瞬きはタイマーだけで行い、14B会話モデルは呼ばない。左ドラッグで移動、ダブルクリックで既存のBreaktail会話画面、右クリックで画面観察・自動観察・終了を選ぶ。

## このPCでの起動

GIFは本番の `Breaktail/assets/gomi_blink.gif` にローカル配置する。画像はGitHubに含めない。

```powershell
# windows_runtime/ で実行する例。現行インストールでは current/ と assets/ が隣接する。
& .\current\start_desktop_pet.ps1
```

起動時に一度画面を見せる場合は `-LookNow` を付ける。右クリックの「今の画面を見て感想」でも観察できる。「画面が変わったら自動で見る」を有効にした場合、ウィンドウ切替をきっかけに、少なくとも2分の間隔を空ける。初期状態では自動観察は無効。

## 観察の範囲

- 4秒ごとのウィンドウ切替はタイトルから種別だけを判定し、文書名やページ名を吹き出しに出さない。反応は30秒以上空ける。ここでは画面内容を読んだと主張しない。
- 画像の観察を選んだ時だけ、画面を一時的に撮り、最大960×540のJPEGをメモリ内で作ってローカルのOllama `qwen3.5:4b` に送る。スクリーンショットとモデルの感想はファイル・会話DB・記憶DB・設定に書かない。Ollamaが使えなければ失敗を表示する。
- 感想は画面に見えることを短く述べる試作で、UIのボタンや文字の正確な理解、ソフトの操作、判断の正しさは未保証。画像の読取りは誤認し得る。

## 手元での初回実測

- GIFは64×64、3コマ、各1000/100/1500ms。Windows画面上でピクセル絵の表示と横移動を目視確認した。
- 既存の9B視覚モデルは合成画像で45秒以内に完了せず。4B視覚モデルをローカルに追加した。合成画像の初回呼出しは93.57秒、ロード済みでの再試行は0.82秒。これは別条件の単発測定であり、モデル間の厳密な比較ではない。
- 実際の画面を最大960×540で撮った単発試行では、撮影0.11秒、ロード済み4Bの感想1.12秒、画像84.7KB。見えた内容への短い感想を返したが、内容の正確さを保証する評価ではない。
- 本番のキャラを `-LookNow` で起動し、ゲーム画面の上でGIFと吹き出しが表示されることを画像で確認。再起動後の実画面観察ではロード済み4Bが0.95秒で短い感想を返した。起動スクリプトの再実行は既存キャラを検出して二重起動しない。既存Web会話は稼働中で、保存済みの会話件数と訂正ファイルの状態は変わらなかった。
- 追加の課題: 初回のモデル読込み待ち、動きの変化、ウィンドウ内容の正確な観察、作業中の邪魔にならない位置、Breaktail本体との安全な連携。一般会話や記憶のM2は別途未完了。

## 追加試作: 画面の部品構造と作業傾向

- [Python-UIAutomation-for-Windows](https://github.com/yinkaisheng/Python-UIAutomation-for-Windows) をこのPCのペット専用依存フォルダーに導入。アクティブなウィンドウのボタン・入力欄・一覧などの種別、左右の配置、親子の深さ、フォーカス種別を最大96部品・深さ3まで読取り専用で調べる。ラベル、入力値、ページ名はモデルに渡さない。遅いアプリのUI Automationに画面キャラを止められないよう、別プロセスを3秒で打ち切る。対応しないアプリは画像認識だけで扱う。
- [OmniParser](https://github.com/microsoft/OmniParser) も確認。スクリーンショット上の要素をより詳しく分ける候補だが、このPCの常駐試作には導入していない。今回の「深さ」はUI部品の親子階層であり、画面の物理的な3D距離を推定したものではない。
- キー操作は短い間隔で状態を調べ、入力・修正・移動・確定・検索・保存・クリップボード操作という分類の12秒間の件数だけをメモリ内に置く。押した文字やキー列、入力欄の値は取らず、ファイルにも残さない。短い押下は取り逃がす可能性がある。操作が続く間は跳ねる頻度を下げ、ひと区切りで短く反応する。右クリックでキー観測を切れる。
- 画面の種別、UIのフォーカス、キー分類を合わせて「入力しているみたい」「ゲームを操作しているみたい」などの暫定的な作業推測を作る。保存キーの押下を実際の保存完了とは呼ばない。右クリックの「いまの観測状態」で、個人の文字列を使わない観測結果を見られる。画像モデルにもこの構造化した補助情報を渡し、手前と背後・左右を区別して短く述べるよう求める。
- 移動は画面を端から端まで横断する方式を廃止。待機中は小さく揺れ、5～13秒ほどの間隔で近くへ跳ね、左右を向き、着地で少しつぶれる。ドラッグ後は置いた場所を新しい拠点にする。
- 匿名の動き・キー分類・画面種別の6テストと構文検査が成功。隔離起動で18秒間の位置を観測し、待機と短い跳躍、左右反転を画面で確認。実画面のUI Automationでは21部品・深さ3を約0.52秒で取得、ロード済み4Bの感想は約1.37秒。本番起動後も別画面で7部品・深さ3を取得した。画面全般の認識精度を示す数字ではない。
- 残る問題: アプリによってUI部品をほぼ公開しないこと、キー状態の短い押下の取り逃し、モデルの画面誤認、作業を邪魔しない反応頻度、Breaktail本体との出典付き連携。

## 追加試作: 位置つき日本語OCR

- [RapidOCR](https://github.com/RapidAI/RapidOCR) とCPU版ONNX Runtimeをペット専用のローカル依存フォルダーに導入。[公式モデル一覧](https://rapidai.github.io/RapidOCRDocs/main/en/model_list/)で日本語に対応するPP-OCRv6 small系を確認した。画像モデル用の縮小画面とは別に、最大1920×1080の画像をメモリ内でOCRへ渡し、文字・信頼度・画面内の位置を取得する。
- OCRは最大12秒の別プロセスで実行し、失敗や未対応画面では既存のUI Automationと4B画像モデルに戻る。OCR結果は最大25行に絞り、連絡先・URL・パス・長い番号・秘密らしい項目を除いてローカルの画像モデルへ渡す。画面画像と読み取った文字は会話DB・記憶DB・ログ・GitHubには書かない。表示中の文字がモデルに対する指示として実行されないよう、参照資料として扱う。
- 合成した日本語UI画像では「設定を保存」「画面を見る」を両方正確に読み、各文字列の位置も返した。隔離プロセス全体4.33秒、OCR推論1.92秒。実画面の単発観察では撮影0.13秒、UIAとOCRの並列観測4.58秒、ロード済み4Bの感想1.58秒、OCR結果は上限25件、UIAは1部品だった。画面種別や小さい文字によって精度が変わるため、これは一般的な正答率ではない。
- 残る問題: OCRはアイコンそのものの意味を検出しない。ゲームのようにUI Automationをほぼ公開しない画面では、画像モデルの見立てとOCRの照合が重要になる。複数画面での誤読・欠落評価、対象ウィンドウだけを読む範囲選択、感想の根拠表示が次の段階。
- 本番のキャラで起動時の観察を実行し、OCR処理の後に吹き出しが表示されるところを画面で確認。感想が長く途中で切れる例を見つけたため、短い一文を促し、長すぎる返答は省略記号を付けて終えるよう修正した。匿名のOCR結果整形と既存キャラを合わせて8テスト成功。これは一回の実画面確認であり、画面認識の正答率評価ではない。

## 継続観察と画面ごとの記憶

- 約0.5秒ごとに48×27の白黒縮小画面を比較する軽い監視を追加。キャラがいる画面下部は変化判定から除外する。変化量が閾値以上の時、前回から4秒以上経っており観察中でなければ、UI構造・日本語OCR・ローカル4B視覚モデルによる詳しい観察を始める。自動観察は初期状態で有効で、右クリックから停止できる。吹き出しは最短12秒間隔とし、観察処理は背後で行う。画面の全フレームを意味理解する方式ではない。
- OCRエンジンは専用プロセスを再利用する。合成画像では初回約2.29秒、2回目約0.57秒。12回の実画面軽量撮影は平均0.04秒、最大0.047秒、静止中の誤変化0回。これは検出処理の速さであり、感想を返すまでの時間とは異なる。
- 成功した感想を画面種別ごとに、最大200種類までローカルの `Breaktail/data/screen_observations.sqlite3` に記録し、同じ感想の再出現回数を数える。右クリックの「最近覚えた画面」から直近の仮の印象を見られる。次回の視覚推論にも「未検証の過去観察」として渡し、現在の画像で照合させる。記録は誤認を含み得るため確定知識として扱わない。画像、タイトル原文、OCR原文、押したキー、会話本文はこのDBに保存しない。既存の会話DB・記憶DB・設定ファイルは変更しない。このローカルDBをGitHubへ送らない。
- 画面下部は軽量な変化検出の対象外なので、そこだけが変わる場面は見逃し得る。画像モデルの初回読込み、アプリのUI公開状況、OCRの難しさによって詳しい観察には数秒以上かかり得る。自動で画面を操作する機能はまだない。
- 本番の画面キャラを更新してPID 47608で再起動し、自動観察がローカルDBに5種類の仮の印象を記録したことを確認した。既存のWeb会話は170件のままで、ローカルOllamaに4Bモデルがあることを確認した。詳しい観察の平均遅延や認識正答率は、継続的な実測をまだしていない。
- 設計の参考: [Generative Agents](https://arxiv.org/abs/2304.03442) は観察を記録・検索する構成を、[MemGPT](https://arxiv.org/abs/2310.08560) は限られた文脈と外部記憶の階層化を示す。ここでは短い画面観察を別DBに上限付きで保存し、同種画面に限って直近3件を検索する部分だけ採用した。論文の反省・計画・重要度検索までは実装していない。画面取得の発展候補はMicrosoftの [Windows.Graphics.Capture](https://learn.microsoft.com/en-us/windows/uwp/audio-video-camera/screen-capture) で、現行実装はPillowの画面撮影を使用する。

## 画面ごとの照合とFisch Wiki（追加）

- 以前の「画面種別が同じなら直近の感想を再利用」では別のRoblox場面も混ざる。画像を8×8の明暗パターンと平均明るさに要約し、種別と見た目が近い時だけ過去の感想を最大3件参照する。元画像は記憶DBに保存しない。距離が遠い画面では「覚えていない」と扱い、見かけが近くても過去の感想は未検証として渡す。これは厳密な画像認識ではなく、似た画面を取り違える可能性がある。
- 旧形式の画面記憶200件は保持し、新しい `scene_observations` テーブルに画像の手掛かり・時刻・再出現回数を追記する。旧形式は右クリックの「最近覚えた画面」で「粗い印象」と明示し、画像モデルへの自動注入には使わない。新形式の上限は2000種類で、上限に達した場合は新規記録を停止し、既存記録を消さない。既存DBのSQLiteバックアップをローカルの作業場所に取得した。GitHubには送らない。
- Roblox画面のOCRで短いFischのアイテム名・場所名が読めた場合、またはローカル4B画像モデルが90秒以上の間隔で候補名を出した場合、[Fisch Wiki](https://fisch.wiki/) のその名前に対応するページだけHTTPSで読む。候補が曖昧、ページ見出しが一致しない、接続に失敗した場合は採用しない。Wikiの題名、短い概要、URL、確認時刻を画面記憶とは別の `wiki_references` に保存し、24時間で再確認する。画面画像やOCR原文はWikiへ送らない。Wikiは非公式のコミュニティ資料なので、ゲームの現行仕様と必ず一致するとは限らない。画面内の文字とWiki本文はモデルへの命令として扱わない。
- 合成画面の類似・非類似、旧DBを残した追加テーブル作成、Wiki候補の選別、出典URL保存の15テストが成功。実際の `Fish Radar` ページの見出しとURLを取得できた。本番キャラは元のGIFでPID 48440として起動。実際のFisch画面での正答率、候補抽出率、Wikiの記述との一致率は未測定。
