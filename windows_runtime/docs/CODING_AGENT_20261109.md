# Breaktailの作業エージェント

会話人格の学習とは別に、既存のOllamaモデルを使う作業ループを追加した。
対象ファイルを読む → 編集する → 検証結果を読む → 失敗を直す → 結果を報告する。
FIO紹介資料の「道具を使い、結果を読んでから書き戻す」という構成を参考にした実装で、FIO本体を導入したものではない。

## 使う

簡易起動は`current/start_agent.ps1`。作業内容を日本語で入力できる。
指定がなければ`projects/agent-work`を使う。テスト実行も任せる場合は`-AllowExecution`を付ける。

```powershell
.\current\start_agent.ps1 -AllowExecution
```

Breaktailのルートから実行する。作業フォルダーはあらかじめ用意する。

```powershell
python current/breaktail_orchestrator.py agent --workspace C:\work\my-project --text "既存コードを調べて不具合を修正して。テストも確認して"
```

既定ではファイルの読み書きとPythonの構文検査まで。Pythonのテストコードを実際に動かす場合:

```powershell
python current/breaktail_orchestrator.py agent --workspace C:\work\my-project --allow-execution --text "不具合を修正し、既存のtest_*.pyを実行して確認して"
```

`--allow-execution`では、対象プロジェクトのPythonコードが利用者の権限で実行される。
ファイル操作の範囲制限はOSの実行サンドボックスではないため、信頼できる作業用コピーで使う。
コマンド実行はPython unittestに限定し、任意のシェル操作は提供しない。

## 現在できること

- フォルダー一覧、UTF-8ファイルの読み取り、新規作成、全文更新、一意な文字列の差分置換。
- 道具名、必須引数、余計な引数、文字列の型を実行前に確認する。未知の道具や不正な引数は副作用を起こす前に拒否し、モデルへエラーを返す。
- 作業フォルダーごとに既存の能力レジストリーへ実際の道具を接続する。実行許可がない場合、テスト実行は登録・利用可能一覧から除外し、実行時にも許可を確認する。
- 読み取った後に他の処理が変更したファイルは、そのまま上書きしない。
- Pythonの構文検査、明示的な実行許可時のunittest、失敗結果を使った再修正。
- モデルへの接続・時間切れ・応答破損等は最大3回の連続失敗で`model_failed`として終了し、途中の変更・バックアップ・失敗の記録を残す。一時的な失敗から回復した場合も失敗回数を残す。自動巻き戻しや自動再開とは別の機能。
- Python編集後の検証漏れや、0件のテストを成功として終了することを防ぐ。
- 最初の変更前ファイル、変更前後のハッシュ、操作の結果、未完了状態を作業フォルダーの`.breaktail-agent/`へ保存。
- 次の依頼で、同じ作業フォルダーの関連する過去の記録を最大3件読み戻す。以前の失敗・変更箇所・検証結果を参照し、内容が前回から変わったファイルを区別する。利用した記憶は各作業の`memory_used.json`に残す。
- 過去の検証成功は今回の成功に流用しない。現在のファイルを読み、今回の変更後に必要な検証を行う。
- 既存の会話・記憶・モデル設定を使い回して変更するのではなく、作業用の記録を別に保持する。

通常のチャットから自動的にファイルを編集する機能は有効にしていない。
作業記憶は同じフォルダー内の実行記録から選ぶ初期実装。会話からの書式の好みは以下の明示接続に限定する。抽象的な原因推定・他のプロジェクトへの自動一般化は未実装。

2026-11-10追加：`check_python`と`run_tests`の検査前後にPython入力のハッシュ一覧を記録する。完了済みの同じ作業内で、失敗→実際の編集→同種の検査成功と最終ファイルが結び付く場合だけ、`observed_recoveries`として失敗・編集・成功のstep番号と出典を次回へ渡す。
テストの変更・削除・追加、空のテスト、時間切れ、証拠不足の旧記録からテスト修正成功を認定しない。原因が分かったことや完全に直ったことは意味せず、今回の検査は省略しない。
現在のPython入力が過去と異なる場合は`current_python_inputs_match=false`。Python以外の資料、外部依存、環境、テストの網羅性は照合範囲に含まれない。モデル自身の修正能力とは別に検証する。

## 会話で指定した作業書式を渡す

Breaktailの会話に、次のような1行だけの発言を保存してから、作業の投入に`--conversation-id その会話ID`を指定する。通常の自由文や過去の人格例から自動で推測しない。

- `作業設定: 報告言語=日本語`（または英語）
- `作業設定: コードコメント言語=英語`（または日本語）
- `作業設定: 説明の長さ=短め`（または詳しく）

同じ項目を後から宣言すると訂正になる。`作業設定: コードコメント言語=解除`のように値を解除にするとその好みだけを外す。古いRaw原文は削除しない。

```powershell
python current/breaktail_orchestrator.py agent --workspace C:\work\my-project --conversation-id cli --text "挨拶関数を作って"
```

`agent-enqueue`も同じ指定に対応する。worker開始時の最新の完了済みRawを読み、今回の作業にだけ渡す。IDを指定しない新規作業へは暗黙共有しない。再開は元の会話IDを保持し、開始時点の訂正を再読取りする。実行中の変更は次回開始まで反映しない。

参照先は選択したdata_root内のRaw。同じIDでも別のdata_rootは別の会話資料なので、投入と実行で同じ設定を使う。直近4MiB・2000行以内の同一会話から、完了済み・人格場面以外・Journalで未確定でない本人の発言を選ぶ。範囲外の古い好みの保持は保証しない。
引用例・assistantの提案・質問・一時的な指定・任意の追加指示は取り込まない。書式の3項目だけで、権限・テスト・完了条件は変えない。今回の依頼と競合すると今回を優先する。
使った原文・turn_id・ハッシュ・訂正先は`preferences_used.json`に保存し、作業結果にも参照情報を含める。モデルの書式追従を強制する完了条件ではなく、必要な品質条件は従来通りchecksに指定する。
CLIの`agent`コマンドから、対象フォルダーを指定した時だけ動く。
学習、人格データの取り込み、モデル切替、既存の記憶削除は行わない。

## 明示した完了条件で終わらせる

CLIの`--requirements-file requirements.json`で、利用者が指定した目標・制約・チェック条件を渡せる。
たとえば次のファイルを用意し、通常のagentコマンドへ追加する。

```json
{
  "goal": "ポートを9090にする",
  "plan_required": true,
  "constraints": ["他の設定を変更しない"],
  "checks": [
    {"kind": "json_equals", "path": "settings.json", "pointer": "/port", "expected": 9090},
    {"kind": "json_equals", "path": "settings.json", "pointer": "/logging", "expected": false}
  ]
}
```

チェックは作業フォルダー内の`file_exists`、UTF-8の`text_contains`、JSON Pointerで選ぶ値の`json_equals`に限定。
JSONの期待値は文字列・有限の数値・真偽値・nullで、型も一致する必要がある。ファイル内容の検査は64KB以下。
条件を満たさないfinishは拒否し、どの条件が合わないかをモデルへ返す。目標と条件のスナップショットを作業記録へ保存し、モデルに変更させない。

これは明示した条件の照合機能。指定しなければ従来の動作であり、自然文から全ての完成条件を自動で抽出する機能ではない。

利用者が固定した既存テストや参照ファイルを維持したい場合は、checksへ`{"kind":"file_sha256","path":"test_calc.py","sha256":"実際の64桁の小文字ハッシュ"}`を指定する。ハッシュは作業前に利用者側で決め、モデルが条件を変更する道具は用意しない。
PowerShellでは`(Get-FileHash -LiteralPath C:\work\my-project\test_calc.py -Algorithm SHA256).Hash.ToLowerInvariant()`で求められる。SHA-256はUTF-8等への変換をせず元のバイト列を照合するため、改行やBOMの変更も不一致になる。対象は64KB以下。
変更したテストを実行して成功しても、この条件が不成立ならfinishは受理されない。キュー・再開でも元の条件を保持する。書込み自体を禁止する機構やテストの品質を証明する機能ではない。指定していないファイルの変更を一律に禁止せず、実行権限も増やさない。
`constraints`の自由文は指示として渡すが自動検証されない。検査したい条件はchecksで表す。存在確認や文字列包含だけでは品質全体を証明しない。

## 工程と依存順序

`plan_required: true`を指定すると、モデルは最初に`set_plan`で工程を作る。各工程にはid、title、前にある工程を指すdepends_on、利用者のchecksを番号で参照するcheck_indicesを含める。計画には全ての完了条件を含める必要があり、モデルに期待値の変更は許可しない。

モデルは道具で作業した後、`complete_step`で工程を実ファイルに照らして確認する。依存先が未完了なら後続工程の完了は拒否する。未完工程の計画修正は可能で、完了済み工程の書換えは拒否する。
検証時に以前の条件が成立しなくなった場合は、その工程と依存する後続工程を未完了へ戻す。全工程を確認するまでfinishしない。
`plan.json`と追記式の`plan_history.jsonl`に計画・進捗・修正理由・検証結果を残す。これは工程管理であり、プロセス終了後の自動再開はまだ含まない。

## 記録からの再開

Pythonの`replace_text`は、元が構文正常な場合だけ、置換候補を保存前に構文検査する。不正になる候補は`ReplacementSyntaxError`で拒否し、元のファイル・更新時刻・バックアップ・変更番号を維持する。`replacement_preview`は未保存候補の該当行とハッシュであり、現在のファイルを表す観測とは区別する。
元から構文不正なPythonは修正の途中を妨げないため、この保存前拒否の対象外。非Pythonは従来の文字列置換。自動的な字下げ補完やコード実行は行わない。全文の`write_file`にもこの制限は適用しない。
保存前の検査が通っても、編集後の`check_python`と、許可している場合の`run_tests`は必要。プレビューは動作・仕様・安全性の検証ではない。

`check_python`と`run_tests`は検査前後のPython入力をハッシュで照合する。テストの終了コードが0でも入力が変わっていれば`ok=false`、`inputs_stable=false`で再検査が必要。`process_ok`と検証成功を分ける。
検査後の変更・追加・削除もfinish時に照合する。作業ツールを通さない変更でrevisionが増えなくても、古い検査成功は利用できない。`verification_inputs`に構文/テストの入力ハッシュと再検査が必要な項目を保存する。再開時に以前の成功は継承しない。
対象は既存の探索範囲内のPython（最大200ファイル）。Python以外のデータ・外部依存・環境・一時的に変更して同じ内容へ戻した状態は保証範囲外。検査後の外部書換えをOSで封じる機構ではなく、観測した時点の照合である。

手数上限、連続モデル失敗、構文エラーの反復停止で正常に記録された未完了の作業は、同じフォルダーとrun_idを指定して再開できる。

```powershell
python current/breaktail_orchestrator.py agent --workspace C:\work\my-project --resume-run-id 保存された32桁のrun_id
```

元の依頼・完了条件・工程を読み戻すため、再開時には`--text`や`--requirements-file`で別の内容へ置き換えない。
途中で変更したファイルとバックアップのハッシュが記録と違う場合は、モデルを呼ぶ前に拒否する。
既存ファイルは再開後に読み直さないと上書きできない。同じ内容への書込みは読取り確認後に無操作とする。
完了済み工程の実ファイルを再検証し、元の工程記録を保つ。同じ親run_idを二度再開することは拒否し、さらに続ける時は新しい未完了run_idを指定する。

`--allow-execution`は自動継承しない。今回もコードのテスト実行を任せる場合は改めて明示する。過去の構文・テストの成功も今回の検証済み状態へ自動継承しない。
この機能追加後のチェックポイントのみ対応し、旧記録、強制終了や電源断でresult.jsonが残らなかった作業、完了済み作業の再実行には対応しない。タスクキューや自動再開とは別。

## 取消と1回の実行の時間予算

構文検査の失敗時は、`syntax_observation`に現在の対象パス・ハッシュ・該当行付近・字下げを保存してモデルへ返す。ソースは資料として扱い、その中の命令を実行しない。範囲外や保護されたパスは読まない。
同じPython入力・行・構文エラーが編集なしで3回続くと`stalled`で止める。無限の再検査を成功扱いにしないための停止であり、自動修正の保証ではない。実際のPython編集または構文検査の成功で反復数をリセットする。別のエラーや内容を変え続けるループには手数・時間予算が適用される。
`stalled`も明示的に再開可能。過去の未完了記録とバックアップを残し、今回の読取り・検証と実行許可は改めて必要になる。

`agent --max-seconds 900`で1回の実行の時間予算を指定する（既定15分、指定範囲0.01〜3600秒）。次のモデル呼出し・道具実行へ進む境目で期限を確認し、モデル待ち時間とPythonテストの待ち時間も残り時間に合わせて短くする。

別のウィンドウから次のコマンドで取消要求を出せる。対象run_idは作業フォルダーの`.breaktail-agent/<run_id>/task.json`で確認する。

```powershell
python current/breaktail_orchestrator.py agent-cancel --workspace C:\work\my-project --run-id 対象のrun_id
```

取消は`cancelled`、期限到達は`time_limit`として未完了の変更と結果を保存する。正常に保存された記録は、利用者が明示した場合に再開できる。自動再開はしない。
これは協調的な停止であり、進行中の接続や検証コードを即座に強制終了する機能ではない。取消後も現在の呼出しが戻るまで待つ場合があり、完了済みの変更は自動で元に戻らない。電源断対策・機器の非常停止・OSの強制的な期限保証とは別。

## 作業をキューへ保存する

`agent-enqueue --workspace 作業場所 --text 依頼`で保存し、`agent-work --workspace 作業場所`で待機中の最初の1件だけを実行する。後者は実行後に終了し、常駐しない。
投入時には`--requirements-file`と、重複投入防止用の`--task-id`（32桁の小文字16進数）も指定できる。同じID・同じ内容は1件として扱い、同じIDで内容が違えば拒否する。
`agent-queue --workspace 作業場所`で一覧、`--task-id`付きで詳細を確認し、`agent-queue-cancel --workspace 作業場所 --task-id 対象ID`で待機取消または実行中の取消要求を出す。

キューは各作業場所の`.breaktail-agent/queue.sqlite3`に保存する。作業実行run_idと結果へリンクする。テスト実行許可は投入内容へ保存せず、workerに`--allow-execution`を明示した時だけ有効。手数・時間予算もworkerごとに指定する。
二重workerをOSロックで拒否する。以前のworkerが結果を保存せず終了していた場合は`interrupted`として扱い、自動的に同じ操作をやり直さない。未完了run_idからの手動再開と、キュー上の状態更新は別であり、自動的には同期しない。

## 現時点の範囲と限界

`search_text {"query":"文字列","path":"."}`で作業場所内のUTF-8を大小区別のリテラルで検索する。行番号・引用・ハッシュと除外/上限情報を返す。検索だけでは編集できず、対象の`read_file`が必要。最大2000項目/200ファイル/200万バイト/40一致行、1ファイル64KB。探索順に上限を適用するため、未探索の範囲が残る場合がある。

`review_changes {}`で今回runの追跡変更を変更前バックアップと現在ハッシュから照合し、読取り差分を返す。外部書換え・欠損・バックアップ不整合は通常の修正と区別する。最大20ファイル/差分合計12000文字で省略を明示。表示では改行を正規化し、末尾改行とUTF-8 BOMを別に示す。この確認だけでは構文/テスト成功にならず、自動復元・削除もしない。全体テストは502件成功、差分道具の実モデル課題は未実施。

`observe_resources {}`で論理CPU数、Windowsの総RAM/使用可能RAM/使用率、作業場所のドライブ空き容量を読取り取得できる。実行許可は不要で、任意コマンドや別の対象パスは受け付けない。既存CapabilityRegistryから実際の取得処理を呼ぶ。
各値に取得元・取得成否を付け、観測時刻を保存する。取得できなかった値を0と推測せず、GPUは未接続と明示する。現在のCPU使用率やGPU使用量を測る機能ではない。値は観測時点のものであり、常駐監視・自動停止・モデル切替は行わない。

初期版の実行検証は標準ライブラリのPythonプロジェクトが対象。
他言語のテキストファイルは編集できるが、JavaScript等のビルドや動作確認はまだ接続していない。
Git操作、依存関係のインストール、外部サービスへの公開、常駐自律作業は未接続。
ファイルは64KB以下、Pythonファイルは200個以下、既定16手・最大40手、テスト実行30秒。
実行の時間切れは子プロセスを終了させるが、テストが生成した別プロセスを全て封じ込める保証はない。
テストが通っても仕様の完全性や安全性は証明できない。モデルによるテスト改変も、人手の差分レビューが必要。
変更後の再読取はするが、自動ロールバックは行わない。途中終了時は保存された変更を確認する。
